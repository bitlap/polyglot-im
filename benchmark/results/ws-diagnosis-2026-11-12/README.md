# WS 连接异常与发压端瓶颈定位（2026-11-12）

[返回压测入口](../../README.md)

## 已确认与尚不能确认的结论

1. **发压端确有瓶颈。** 双实例、同一组 128 用户和设备、总并发 128 下，1 个 Python 进程合并约 77.45 条/秒，4 个进程约 201.87 条/秒（2.61 倍）；合并原始延迟的 p99 从 6836.58ms 降至 3573.06ms。服务未变，不能把原先的低吞吐直接当作后端容量。
2. **http4s 0.23.30 的自动 Pong 与数据帧存在并发写入交错。** 客户端 Ping 间隔缩至 50ms 时，6 条连接出现 ConnectionClosedError，客户端发送 1002 协议错误关闭码，8 条消息未确认。0.23.38 对整帧写入及关闭状态使用互斥保护；升级后相同 128 连接、50ms 心跳的 3 轮均无连接错误或未确认消息。
3. **压测器隐藏了接收异常。** 原来 finally 中 cancel + gather(return_exceptions=True) 丢弃接收任务的结果，发送端仍继续写入，最后只有排空 TimeoutError。现检查接收任务状态、传播原异常，并记录逐连接关闭码与未确认计数。真实设备会话撤销实验捕获 ConnectionClosedError/1006 和 3 条未确认，未再误归为 TimeoutError。
4. **历史 32 条仍保留为原因未证实。** 正常心跳重跑 6 轮共 37,223 条均收到；这不能否定历史失败，也不能证明其全部由上述依赖问题导致。历史原始记录没有接收异常、关闭码或抓包，无法补造这一证据。

上游 [0.23.30 实现](https://github.com/http4s/http4s/blob/v0.23.30/ember-server/shared/src/main/scala/org/http4s/ember/server/internal/WebSocketHelpers.scala)中，自动 Pong 和发送流分别调用未加锁的 writeFrame，而一帧由多个 socket.write 完成；[上游修复提交](https://github.com/http4s/http4s/commit/296eb99d7b30)明确处理两者交错，[0.23.38 实现](https://github.com/http4s/http4s/blob/v0.23.38/ember-server/shared/src/main/scala/org/http4s/ember/server/internal/WebSocketHelpers.scala)保护整帧及关闭状态。这里的 1002 + 源码 + 升级对照支持该诊断；没有把未知历史失败追认为已证实的同一原因。

## 环境、顺序与证据边界

使用 ed33f07 的 0.1.1 业务代码，在隔离工作树补充压测诊断；升级前 http4s 0.23.30，升级后只将三个 http4s 依赖统一改为 0.23.38。业务 WS 路由和持久存储没有重写。双实例，总业务连接池 8、JVM ActiveProcessorCount 4、最大堆 2048MiB，256 个测试用户、16 个生产者；APNs Worker 关闭，仍写 Outbox，PostgreSQL 三项落盘设置开启。与历史矩阵共用同一台 Mac，非独占主机，无 CPU 绑核或物理配额。不是生产最大容量结论。

先在同一临时数据库预置每用户 20 条历史，依次做正常心跳 6 轮，再做四轮发压进程对照（4/1、1/4），之后撤销设备和高频 Ping，再做函数剖析。升级后重建临时数据库，不额外预置历史，做三轮高频 Ping。数据量与系统负载存在差异，因此高频 Ping 只比较帧/连接正确性，不比较升级前后吞吐提升。

多进程对照使用相同的前 128 个用户：每进程 32 条连接，user_offset 保持 benchmark-0…127 设备身份不变；每条连接的 HTTP 写入与 WS 分配在不同节点。各进程协议预热后由父进程同时释放；数据库只由父进程观测一次。各轮持续发送 60 秒，耗时包含建连及末尾排空；每个工作进程均正常退出。

正常复现使用早期“只补记录、保留原等待行为”的诊断版；后续对照、控制实验和剖析使用传播接收异常的修复版。生成器对照原始 metadata 保存 runner_sha256；升级后高频实验保存 server_build_sha256。私有接入文件包含随机凭证，不发布。

## 函数剖析

[完整函数统计](profile.txt)、[原始 cProfile 文件（gzip）](profile.prof.gz)、[该轮消息记录](profile.json.gz)。使用同一夹具、128 连接，先协议预热，再对 ws_trial 建连、15 秒发送窗口和排空整体开启 cProfile；261 条均收到。受剖析开销影响，该轮总耗时 40.81 秒，不纳入容量对照。

| 函数/调用链 | 次数 | 累计或自身耗时 | 含义 |
| --- | ---: | ---: | --- |
| _assign_requests_to_connections | 2822 | 累计 23.448s | 同步分配、扫描共享 HTTP 连接池，占该次剖析总耗时约 57.5% |
| connection.has_expired | 58609 | 累计 15.478s | 扫描时对每条连接做过期/可读检查 |
| is_socket_readable | 27006 | 累计 10.359s | 大量 socket 可读性探测 |
| select.poll.poll | 27006 | 自身 9.530s | 可读性探测进入系统调用；此项是剖析计时，不是 CPU 调度等待 |
| connection.is_idle | 688456 | 累计 1.942s | 重复遍历与空闲状态检查 |

累计耗时包含子调用，以上各行不能相加。cProfile 的计时及开销不能直接解释为正常运行 CPU 占比。结合 1/4 进程对照，可确认本实现的共享 HTTP 池管理在发压端事件循环里占用了大量同步时间，延后同一循环上的 WS 接收与 ack。对应 [HTTPcore 1.0.9 源码](https://github.com/encode/httpcore/blob/1.0.9/httpcore/_async/connection_pool.py)在请求加入/移除时扫描连接及排队请求，部分空闲统计有嵌套遍历。尚未给其他平台或版本做同类剖析。

## 复现命令与回归

分别在检出对应依赖版本的工作树启动专用夹具；接入目录必须是新的私有目录。以下 $PRIVATE_CONFIG 指向该目录的 config.json，不指向业务或生产服务。

```sh
uv run --project python-client --locked python -m benchmark.run \
  --serve-only /tmp/im-ws-fixture-private --instances 2

# 另一终端，夹具启动完成后执行；固定同一组 128 个账户及设备。
uv run --project python-client --locked python -m benchmark.ws_generator_probe \
  --config "$PRIVATE_CONFIG" --output /tmp/ws-generator-probe.json.gz \
  --concurrency 128 --duration 60 --repeats 2

uv run --project python-client --locked python -m benchmark.ws_ping_probe \
  --config "$PRIVATE_CONFIG" --output /tmp/ws-ping-probe.json.gz \
  --concurrency 128 --duration 30 --ping-interval 0.05 --repeats 3
```

本报告的单/四进程对照之前另用正常 run 预置每用户 20 条历史并运行 6 轮；命令本身不会重建该数据集，数据准备差异不能忽略。新增真实 TCP 回归使用 JDK WebSocket 接收持续文本，同时发送 500 个 Ping，检查文本不损坏、所有 Pong 收到。同一测试临时将依赖切回 0.23.30 后失败，JDK 报 Unexpected rsv1 bit；0.23.38 下通过。见[旧版失败日志](regression-before.log)与[新版通过日志](regression-after.log)。这种独立于 Python 压测器的复现进一步确认服务端帧交错。Python 回归覆盖静默连接超时、正常提前结束、解析异常、心跳关闭及连接准备失败。

最终 `just check` 全部通过：Python 67、uni-app 5、Dart 21、Flutter Client 11、Flutter 示例 1、Scala Client 18、Scala Server 45、benchmark 41，共 209 项；包含升级后的服务集成测试和新帧并发回归。

本目录的 [哈希清单](sha256.json)用于核对原始数据与日志；未发布任何接入文件、令牌、票据或数据库连接配置。
