# 消息一致性与可达性契约

Polyglot IM 的可靠消息链路采用**允许重复的至少一次同步、服务端幂等写入和客户端状态去重**。它不提供端到端“恰好一次（Exactly-once）”投递或业务执行保证。至少一次的恢复能力以消息已提交、数据仍保留、有效身份与网络恢复、客户端继续同步为前提；不承诺在任意故障下必达，也没有固定送达时限。

本契约适用于已实现的业务通知、文字与 Unicode 表情单聊，以及默认持久化适配器。使用 VolatileStore、替换适配器或自行处理同步时，宿主必须承担相应的持久化与恢复责任。

本文集中维护消息保证与故障恢复语义；[系统架构](architecture.md)说明组件和数据流，[多实例部署](distributed.md)说明协调机制及配置，[业务接入](integration.md)提供 Outbox 用法。

## 三种语义的区别

| 语义 | 含义 | 本项目的选择 |
| --- | --- | --- |
| 至多一次（At-most-once） | 不重试可能丢失的发送，接收零次或一次 | 不作为可靠消息链路的默认策略 |
| 至少一次（At-least-once） | 在可恢复条件下持续重试或补拉，允许重复接收 | 持久事件同步与业务 Outbox 的恢复模型；必须满足下文前提 |
| 恰好一次（Exactly-once） | 在约定边界内，处理效果既不丢失也不重复 | 只对特定事务内的幂等写入效果作约束，不作为跨网络、App 回调、APNs 或业务副作用的整体承诺 |

同一消息收到两次但缓存中只有一条，是“重复投递后去重”，不能据此称网络只投递了一次。若请求始终被权限/参数校验拒绝，或者客户端停止重试，至少一次的条件不成立。

## 各链路保证

| 环节 | 实际保证 | 前提与边界 |
| --- | --- | --- |
| 业务事务 → 生产方 Outbox | 业务变更和发送意图在同一个 PostgreSQL 事务提交或回滚 | 必须调用 enqueue 加入宿主事务；直接写业务库再调用 HTTP 存在双写缺口 |
| 生产方 Outbox → IM | pending 意图可租约接管并重复发送；固定幂等键使重复请求归并为同一条消息 | 宿主持续运行 Worker；修复身份/网络问题；参数、权限、冲突等永久错误可能进入 dead，须处理后以原键重放 |
| 客户端直接发送 → IM | 单次调用有限重试；同键重试在服务端只创建一条消息 | Client 没有默认持久化待发送队列；发送意图未保存便退出 App，不能保证以后自动补发 |
| IM 事务 → accepted | 成功响应之前已提交消息、相关事件、计数及当时符合条件设备的推送任务 | 这是服务端接受确认；不表示设备收到、用户看到或业务已处理；耐久性还受数据库配置与故障切换约束 |
| 持久事件流 → 设备缓存 | 从有效本地游标按序补拉，可重放、可重复；消息和游标原子提交，重放不重复增加缓存消息 | 客户端继续运行同步，数据在保留范围内，存储提交成功；首次快照与过期重建有单独范围，见下文 |
| 设备 ack → 服务端 | 单设备接收水位只增，重复 ack 安全 | Client 在本地提交后才 ack；服务端不能验证自定义客户端是否真的落盘；ack 不等于已读 |
| IM → APNs → 用户 | 有界重试的尽力提醒，可能重复、合并、延迟或不到达 | 无有效 token、未授权、静音、已读、登出可不发送；达到 10 次领取预算进入 dead，不保证至少一次成功送达 |
| Client 更新 → 宿主业务处理 | 提供缓存状态更新与已读 API | 不提供业务回调或外部副作用的恰好一次执行；设备 ack 不是业务处理确认 |

生产方 Outbox 与 APNs Outbox 的停止条件不同，不能把后者的 10 次预算套用到前者。APNs 接受一次请求后响应丢失，重试可能再次提醒；租约标识只能隔离数据库回写，无法撤销已经发出的网络请求。

## 服务端幂等与“只创建一次”的范围

发送前生成稳定的 `client_message_id`；对同一发送意图，超时、重连、换实例和手动重试都保留原键及原内容。通知和单聊各自在自己的发送域中，按 `(app_id, sender_id, client_message_id)` 去重；两个域使用不同消息表，不提供跨接口去重。单聊域内跨会话使用同一键也视为同一意图。

首次创建返回 HTTP 201；同键同内容返回 HTTP 200 和原 `message_id`，不再增加消息序号、未读计数或推送任务。同键更改接收者/会话或内容返回 409 `IDEMPOTENCY_CONFLICT`。新键代表新的发送意图，即使文字完全相同，也会创建新消息。

若事务未提交便失败，不产生部分消息事实；若事务已提交但响应丢失，发送方只能判定“结果未知”，不能把超时当作未发送。用原键重试才能查询并收敛到原结果。默认维护任务不删除消息和幂等记录；运维若删除这些记录，或灾难恢复回退了数据库，则不再保证历史重试仍能去重。

这里的“只创建一次”是**保留期内、已成功接受的同一发送意图在 IM 数据库中的效果**，不包含发送前丢失的草稿、网络传输次数、每设备提醒次数或宿主后续操作。

## 一致性与顺序

服务端共享一个 PostgreSQL 写主库。业务通知在同一事务更新消息、接收用户事件、水位和推送任务；单聊在同一事务更新会话消息、双方事件、会话版本、未读与接收方推送任务。失败整体回滚，不存在只写了一方事件便返回成功的中间提交。

| 范围 | 顺序与读取语义 |
| --- | --- |
| 同一单聊会话 | 会话行锁协调，`conversation_seq` 按事务提交顺序递增；并发发送谁先拿到协调锁谁先排序，不按客户端时间或请求发起时间排序 |
| 同一用户事件流 | 用户状态锁协调并在事务内分配位置；通知、单聊、已读共用账户游标，按位置升序补拉 |
| 不同用户/会话 | 不提供全局总序；双方设备收到同一条消息的时间可以不同 |
| 单次快照/增量响应 | 主库 REPEATABLE READ 一致性快照；水位与数据属于同一查询快照 |
| 多个 HTTP 请求及多台设备 | 各请求可读到不同提交时点；设备缓存最终追上主库，不保证同时刷新。增量页的计数可先于该页消息，须追完 has_more |
| 已读和缓存合并 | 已读水位只前进；旧响应不回退会话版本/同步位置，重放按消息标识合并。HTTP 历史响应不推进账户游标 |

通知已读位置为 `max(old_read, requested_read)`，且不超过服务端消息高水位；通知未读数为 `latest_seq - read_seq`。全部已读以请求前捕获的位置为界，后来到达的通知保持未读。单聊未读只统计对方未读消息，不能用这条减法计算，字段规则见[单聊状态](direct-chat.md#状态同步与缓存)。

这是按用户/会话协调的原子写入与快照读取，不是整个系统的全局串行化或跨业务数据库的分布式事务。同步等可靠查询必须访问写主库；接到异步只读副本会破坏本契约的读取前提。

## 断线、ack 与离线恢复

HTTP 补拉与 WebSocket 读取同一持久事件流。NOTIFY 只是提交后的唤醒提示，漏掉提示不删除消息；监听重连、订阅初始补查和默认每五秒协调检查负责重新查库。五秒是协调周期，不是端到端延迟上界，仍受排队、网络、数据库和设备调度影响。

WebSocket 在连接内按已发送位置继续读后续页，**没有逐消息等待 ack 后才发下一条，也没有对每条未 ack 消息定时重发的机制**。恢复依赖客户端持久游标：重连先 HTTP 补拉，再带本地游标建立 WS；服务端记录的设备 ack 不能替代本地缓存游标。

| 故障点 | 恢复结果 |
| --- | --- |
| 发送方在收到 accepted 前断线 | 提交结果未知；以原键重试，返回原消息或完成首次创建 |
| 已接收页面，本地提交前崩溃/存储失败 | 本地游标未前进，恢复后从旧位置重新拉取 |
| 本地提交后、ack 发出前崩溃 | 本地消息已保存；恢复使用已提交游标，无需依赖 ack 成功来保住消息；旧页面再次到达也可去重 |
| 服务端实例崩溃或漏掉 NOTIFY | 连接重建到任一实例，从共享持久流恢复；数据库必须可用且数据仍在 |
| 业务副作用完成后、宿主处理记录提交前崩溃 | 可能重复执行；宿主需让副作用与去重记录同事务提交，或对外部系统使用幂等 API/业务 Outbox |

首次登录不是逐条重放所有历史事件。快照只带最近 100 条通知和至多 100 个会话摘要，不包含单聊历史；通知历史、剩余会话和单聊历史须分页读取。事件清理导致游标早于保留水位时返回 410 `RESET_REQUIRED`，Client 重建快照再追增量。重建恢复的是保留数据的状态，**不保证每一条旧事件都再次触发回调**，也不能恢复已被运维删除的历史。

默认维护不自动清理可靠事件，另有显式运维清理入口；接入方须制定消息、事件和幂等键的保留政策，并覆盖允许的最大离线/重试窗口。未知事件可保留兼容并推进游标，不代表旧版客户端已经理解或执行了新业务。

## 可达性与确认的边界

`accepted` = IM 已提交；设备 ack = 客户端报告某个接收水位；`read` = 客户端报告实际阅读水位；APNs success = 提供方接受请求。它们不能互相替代，也不能证明用户本人已看到屏幕。面向发送者的独立设备 delivered 回执尚未实现。

已提交消息在网络恢复、身份有效、客户端持续补拉、服务器/本地存储可用且数据未过保留范围时，可以最终进入设备缓存。用户长期不打开 App、系统禁止后台运行、权限失效、设备空间不足或推送被禁用时，不承诺某个时间前可达。每台设备分别同步，一台设备 ack 不代表其他设备已接收。

数据库不可写或发生分区时，应用拒绝成功写入，不在各实例内存中接受相互冲突的消息。主机故障后已确认数据是否保留，取决于 WAL 持久化、同步复制、旧主隔离及切主策略；默认应用多实例本身不提供 RPO=0。详细部署要求见[数据库高可用](distributed.md#数据库高可用)。

## 接入要求与验证证据

发送方应持久保存需要跨重启恢复的发送意图与幂等键；业务事件优先采用[生产方 Outbox](integration.md#业务事务-outbox)。接收方使用可靠 LocalStore，原子提交状态和游标，持续处理分页与重连；不要把 UI 回调当作可靠消费队列。业务处理需独立的持久去重记录与事务边界；对完整事件消费有要求时，不能仅依赖有限快照或 App 缓存更新。

现有测试覆盖：

- [StoreSuite](../scala-server/src/test/scala/polyglot/im/server/StoreSuite.scala)：事务、幂等、单调已读、过期游标与推送抑制。
- [DistributedStoreSuite](../scala-server/src/test/scala/polyglot/im/server/DistributedStoreSuite.scala)：跨连接池去重/顺序、快照一致、监听恢复、无通知补拉、租约接管和重试预算。
- [MultiProcessSuite](../scala-server/src/test/scala/polyglot/im/server/MultiProcessSuite.scala)：跨 JVM 唤醒与进程强杀后恢复。
- [端口替换测试](../python-client/tests/test_ports.py)：自定义缓存/Socket 下提交先于 ack，以及会话释放；各端也有对应缓存失败和重放测试。

这些证据不包括 Apple 真机必达、跨地域分区下持续可写、数据库主备切换零丢失或任意业务副作用的恰好一次执行。验证命令与环境见[验证记录](verification.md)，容量与延迟见[基准报告](../benchmark/README.md)。

## uni-app 默认适配器

uni-app 与其他 SDK 使用同一消息、会话、游标和阅读语义。默认存储串行保存整个账号缓存，成功后才确认；受小程序配额限制，失败不推进游标或内存，不静默截断已加载历史。实时处理最多排队 32 帧，超出则断开并 HTTP 补拉；网络重试有界，重连先同步。关闭取消默认请求及等待；后台暂停实时与轮询。设备偏好 API 不负责取得原生 APNs token，微信订阅消息未实现。详细配置与显式退出参数见 [uni-app 文档](client/uniapp.md)。
