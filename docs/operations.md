# 安全与运维

## 当前边界

初始化服务没有用户认证和业务路由，默认只绑定本机。不得将其作为公网生产 IM 服务。以下为后续实施要求。

## 授权与输入防护

- 所有操作以 app_id 隔离；客户端传入的 user_id、sender、role 不能决定认证身份。
- 用户令牌与服务凭证分开；机器人只获批指定会话、消息类型和频率权限。
- 历史、搜索、附件下载、引用与转发都校验同一可见性策略。
- 写事务内检查退群、禁言、拉黑和发送限制，防止检查后状态变化。
- URL 卡片抓取限制域名/协议、重定向与内网地址，防 SSRF；富文本净化，文件扫描。
- 限制文本字节、附件体积、群成员数、批量收件人、WS 帧与连接缓冲；数值须公开并压测后设定。

## 推送与隐私

每设备记录平台、提供商、token 更新与失效状态。用户退出解绑、令牌泄露撤销、权限拒绝不影响站内消息。通知默认避免锁屏显示敏感正文；推送提供商接收不计作设备已送达。

APNs、FCM、厂商通道分别适配；移动后台和强制退出存在系统限制，见 [Firebase Flutter 消息接收说明](https://firebase.google.com/docs/cloud-messaging/flutter/receive-messages)。冷启动点击应先恢复登录、校验当前用户、补拉并验证目标，再交由宿主导航。

## Webhook

允许列表控制目标；HMAC 签名覆盖时间戳和原始请求体，订阅者验证时间窗与 event_id 防重放。使用指数退避、有界重试与死信；人工重放保留原事件身份及新尝试身份。日志不输出密钥和完整敏感正文。

## 观测

建议记录：HTTP/WS 活跃连接、握手错误、鉴权失败、发送提交延迟、Outbox 积压/最老事件年龄、同步落后、游标重置率、重复投递率、推送通道错误与 token 失效、数据库锁等待、慢消费者断连、Webhook 死信。

request_id、message_id、event_id 贯穿链路；用户身份需脱敏。指标标签不放高基数 message_id。存活、就绪、业务投递成功率分别监控。服务目标由真实负载测试后确定，初始化不承诺“百万连接”。

## 故障恢复

| 故障 | 预期行为 |
| --- | --- |
| API 提交后响应丢失 | 原幂等键重试返回原消息 |
| Worker 崩溃 | 租约过期接管，重复投递由消费者去重 |
| Redis/通知通道中断 | 可靠事件保留；恢复后补拉；不丢唯一消息副本 |
| 网关重启 | SDK 带游标重连 |
| 本地数据库事务失败 | 不确认事件；恢复后重新消费 |
| 长离线或数据清理 | RESET_REQUIRED，快照追增量 |
| 推送通道故障 | 重试/降级与告警；站内消息仍可恢复 |

## 数据留存与删除

按应用明确消息正文、附件、事件、幂等记录、审计及备份的保留周期。清空 UI、用户隐藏、服务端物理删除与备份过期不是同一能力。删除策略必须覆盖搜索索引、对象存储、Webhook 副本和审计政策。引用和撤回不能保留被禁止展示的正文摘要。

备份恢复需定期演练并验证消息与游标一致性；恢复后可能产生重复事件，SDK 去重仍然必要。未完成演练前不声称满足特定 RPO/RTO 或合规认证。
