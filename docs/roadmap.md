# 实施与验收

## 优先级原则

以现有 sf-app 的消息提醒闭环为第一目标：业务服务产生通知，App 展示消息、显示未读、标记已读，断网或重启后可恢复；之后补齐前台实时更新和后台系统提醒。首批业务场景为创作成功/失败、评论/回复、点赞/收藏和系统通知，按实际业务事件逐个接入。

当前排序只调整实施计划，不代表新增功能已经实现。优先级由高到低为 P0 → P1 → P2 → P3；同级按下方依赖顺序推进。**App 站内可用版本以 M1 为门槛，包含后台提醒的首个完整 App 版本以 M1 + M2 为门槛，不等待单聊、群聊或撤回。**

## 阶段与交付门槛

| 优先级 / 阶段 | 范围 | 退出条件 |
| --- | --- | --- |
| 已完成基础 / M0 | 当前骨架、协议、中文文档、just、CI | 三端编解码和格式检查、包构建、健康检查通过 |
| P0 / M1 App 站内消息闭环 | 用户/服务鉴权、通知持久化、幂等与 Outbox、列表分页、同步、未读/已读、基础本地缓存、账号隔离、Scala/Python 通知发送与 Flutter 接入 | 业务事件可见、消息不重复、未读准确；刷新/回前台/断网恢复可补拉；退出与切环境不串数据 |
| P1 / M2 App 提醒体验 | WS、心跳与重连、后台推送、设备 token、通知点击/冷启动、基础静音与多设备已读同步 | 前台实时更新；目标 iOS/Android 渠道真机验证；权限拒绝时站内仍可用；点击恢复账号和同步后打开正确内容 |
| P2 / M3 单聊与通用增强 | 单聊文本与媒体、会话管理、草稿、回复引用、私聊回执、设备管理及在线/输入状态 | 用户发送权限、私聊失败重试、媒体访问、用户输入治理和基础会话操作通过 |
| P3 / M4 群聊与高级能力 | 群消息、角色/审批/禁言/@、群回执、撤回、编辑、搜索、回应、转发、TTL、机器人、Webhook、大群 | 按功能矩阵逐项验收；群权限、消息变更、索引一致性和故障恢复有证据 |

基本鉴权、应用/用户隔离、限流、日志脱敏、可靠落盘和必要留存政策属于 M1 的交付门槛；用户生成内容与媒体所需的拉黑/举报/审核和扫描随 M3 上线，不能因为“高级治理在后面”而推迟这些前置要求。

## P0 实施顺序：先让 App 真正收到和管理通知

| 顺序 | 任务 | 具体交付与验证 |
| --- | --- | --- |
| 1 | 明确 App 通知契约 | 定义 task.completed / task.failed、评论/回复、点赞/收藏、系统通知的 payload、计数规则及受控 action；补充 Schema、样例及三端模型 |
| 2 | 接入用户与服务身份 | 复用现有业务登录，限定应用/用户作用域；Scala/Python 服务身份只允许发送授权通知 |
| 3 | 实现数据库与可靠写入 | 迁移、通知会话、消息、用户事件、已读位置和 Outbox；提交后再确认；业务生产端 Outbox 覆盖跨系统双写 |
| 4 | 打通服务端发送 | Scala、Python 提供可测试的通知发送入口；稳定幂等键；先以任务完成/失败走通端到端，再增加评论等事件 |
| 5 | 提供列表与可靠同步 | 历史分页、增量游标、去重、过期快照与未知类型回退；新旧通知接口读取同一份数据 |
| 6 | 实现 Flutter SDK 基础 | HTTP 接入、移动端持久缓存与游标同事务提交、Web 存储适配或明确降级、错误/空态/加载状态；恢复前台主动同步 |
| 7 | 实现未读与阅读确认 | 服务端维护计数；已读水位只增；红点联动；“全部已读”限定在操作时捕获的服务端水位，不误清之后到达的消息 |
| 8 | 接入 sf-app 消息页 | 替换现有分页通知来源，展示时间/内容/阅读状态；点击业务资源先鉴权、再受控导航；资源删除/无权限有占位 |
| 9 | 完成账号与网络恢复 | 退出取消任务和重试，按环境/用户隔离缓存，迟到回调不污染新账号；断网、超时、重启可恢复 |
| 10 | 验收首个站内版本 | Scala/Python 真实事件 → 持久化 → Flutter 列表 → 红点 → 已读 → 重启恢复；不依赖 WS 或系统推送完成正确性验证 |

通知中的作品缩略图、资源身份和跳转可引用已有业务资源，不必先实现聊天图片/语音上传。App 此阶段是业务通知接收者，不要求用户发送聊天消息；完整聊天发送 UI、草稿和私聊回执放到 M3。

Scala/Python 的通知发送和 HTTP 查询契约、Flutter 的接收与阅读契约在 M1 一起验证；Scala/Python 通用长连接客户端、机器人消费不阻塞 App 接入。协议仍保持三端一致，不为 App 临时发明私有线格式。

## P1 实施顺序：补齐实时与后台提醒

1. 在同一持久事件流上增加 WS、稳定同步水位、心跳、退避重连和背压；连接失败时 HTTP 补拉仍有效。
2. 增加设备注册、推送 token 更新/失效/退出解绑；按 App 实际发行渠道接 APNs、FCM 或必要厂商通道，不要求所有渠道齐备才接入 App。
3. 实现前台提醒去重、后台展示、冷启动点击、通知权限拒绝、基础静音和通知隐私；系统角标按平台能力适配，站内红点为一致性基准。
4. 同步多设备已读位置，验证前后台切换、断网后恢复、用户退出和切换账号的推送目标。

高级分时段免打扰、@提醒例外、Web/桌面系统推送可后置，不阻塞目标移动渠道上线。任何“通道已接受”都不当作用户已送达或已读。

## P2 / P3 后续顺序

M3 先做文本单聊、必要的用户关系限制及举报，再补图片/文件、语音/视频、回复引用、会话置顶/草稿/归档与私聊回执，最后补在线/输入提示。聊天媒体上传与审核和对应类型一起交付。

M4 先按实际业务需要选择群聊或消息撤回/编辑，再增加群管理和群回执、搜索、回应、转发、定时/TTL、机器人与 Webhook。大群、复杂扇出、音视频通话和 E2EE 均不进入 App 基础通知版本的关键路径。

## 横向验收场景

按功能所在阶段执行，不要求为尚未上线的群聊/撤回提前实现完整测试系统。M1 必须覆盖身份隔离、事务、幂等、可靠同步、未读/已读与恢复；其他验收随对应阶段进入门槛。

- **跨语言**：共享合法/非法样例、大序号、未知类型、新可选字段、协议主版本不兼容。
- **写入一致性**：并发重复发送、同键不同内容、事务回滚、提交后断连、Worker 重启。
- **同步一致性**：握手同时新写入、并发事务反序提交、乱序/重复、慢消费者、游标过期、撤回后快照。
- **多设备**：A 已读后 B 更新、设备注销、账号切换时旧响应到达、浏览器多标签。
- **群权限**：退群/禁言与发送并发、管理员越权、新成员历史、解散后附件和搜索。
- **媒体**：断点/失败上传、扫描未完成、恶意文件、签名过期、跨会话转发权限。
- **推送**：前台/后台/强退、token 轮换、权限拒绝、免打扰、冷启动、重复点击、账号不匹配。
- **运维**：Redis 不可用、数据库恢复、Outbox 积压、推送故障、Webhook 死信、备份恢复。

## 性能基线

压测前记录目标在线设备、每秒消息、群规模、消息大小、离线时间、扇出分布及数据库配置；分别测提交延迟、在线投递延迟和离线追赶时间。结果应包含 p50/p95/p99、错误率和资源占用。初始化阶段不使用未经测量的容量数字作为承诺。

## 兼容与发布验收

构建成功不等于可集成：每次正式发布须从产物安装到独立示例工程，验证 SDK 导出 API 和最小使用方式。Schema 与文档变更同时更新契约测试。真实通知接入 sf-app 时保留旧 messageId 映射，由同一可靠存储供新旧接口读取，避免双写产生不同消息事实。
