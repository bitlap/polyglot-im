# 历史敏感通知清理

`tools/purge_notifications.py` 按业务方导出的精确清单，清除 IM 中已泄露身份的通知。它只连接 IM 专用数据库，不查询业务表，不改变协议或客户端包版本。普通运行只读预览，只有 `--apply` 才写入。

清单为 JSON 数组，每条仅含 `user_id`（收件人）与 `client_key`（生产者幂等键），每份1至1000条。命令还要求明确 `--app` 和 `--sender`，三重范围同时匹配才处理。输出只有请求、匹配和变更数量，不输出正文或身份。空清单不执行；不匹配的记录可能未送入 IM，须与业务方核对。

操作顺序：

1. 暂停业务通知 Worker 和 IM 推送 Worker，等待在途请求结束，阻止旧负载继续投递。先部署业务端匿名化并清理其待投递负载，再导出清单。限制清单文件权限，勿提交仓库。
2. 用 IM 自己的凭证设置 `IM_MAINTENANCE_DSN`，保存受控数据库备份并预览每份清单。不要通过命令参数传密码。
3. 核对应用、生产者和数量后，显式执行同一清单；完成并核对后恢复 Worker。重复执行已清理记录不会再次推进游标。

```sh
uv run --project python-client --locked python tools/purge_notifications.py \
  --app <app-id> --sender <producer-user-id> --manifest /secure/manifest.json
# 核对后，在同一条命令末尾添加 --apply 执行。
```

写操作锁定账号状态，在单一事务内清空消息及历史同步事件的负载、标为已读和删除、取消相关推送任务，更新未读计数并写入有新版本的 `notification.updated` 墓碑及同步唤醒。其他通知、全局已读水位和会话序号不变；任何失败全部回滚。清单跨页分别提交，失败页可重试。

客户端重新同步后用墓碑清除原负载，离线设备仍可能保留尚未同步的旧副本。已经显示或已被查看、截屏的系统通知无法靠数据库清理撤回。回滚敏感负载会恢复泄露，恢复备份前必须再次脱敏。

验证：`just test-maintenance` 默认仅运行输入校验，数据库用例明确跳过；使用自有本地临时库 `im_privacy_test` 设置 `IM_MAINTENANCE_TEST_DSN` 后运行，验证预览只读、范围隔离、旧事件脱敏、推送取消、未读准确、同步墓碑、幂等与事务回滚。测试会重建该专用库的 `snap_flow` schema，不允许使用业务或生产数据库。
